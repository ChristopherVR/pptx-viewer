# Limitations

::: warning Read this before adopting
`pptx-viewer` covers a large surface of the OpenXML specification, but some things are approximated, read-only, or bounded by the browser platform. This page lists only what you **cannot** do, or can only do partially. Anything not listed here loads, edits, renders and saves; see [OpenXML conformance](/architecture/openxml-conformance) for the formal coverage manifest.
:::

| Element coordinates                                    | Byte-exact; one combined rotated edit lands within 2 EMU, proven inherent to PowerPoint itself | Positions and sizes are exposed as whole pixels (9,525 EMU per pixel), but the exact source EMU is kept alongside (`xEmu` / `yEmu` / `widthEmu` / `heightEmu`): an unmoved element, and an unmodified group at any nesting depth (its own placement, `a:chOff` / `a:chExt` and every child), re-emit their source `a:off` / `a:ext` / `a:chOff` / `a:chExt` byte-for-byte on save, whatever child-space convention the file used. Resizing a group directly keeps its child space and every child byte-identical, exactly as PowerPoint does (COM-verified). Moving or resizing a child keeps the group's original child space (untouched siblings stay byte-identical) and, like PowerPoint's own bounding-box auto-fit, tightly re-wraps the group's own `a:chOff` / `a:chExt` and `a:off` / `a:ext` around the new set of children, propagating up through every enclosing ancestor whose own box changed as a result; this is COM-verified byte-exact for a plain move, a rotated child (rotating alone has no effect, matching PowerPoint), a rotated group (the fixed rotation pivot is reproduced), nested-group propagation, an unrotated group resized directly AND having a child edited in the same save, a ROTATED group resized directly AND having a child moved+resized in the same save, and a rotated shape that is itself a direct child of a group, resized rather than moved -- including when its width and height are BOTH resized together in one edit (COM-verified byte-exact across 25 / 37 / -40 / 61 / 113 / 155 / 200 / 290 degrees: matching PowerPoint requires composing the rotation-aware resize as two sequential per-axis corrections, width then height each re-anchored against the previous step's result, not one simultaneous rotation). A directly resized ROTATED group (no child touched) is byte-exact too: COM ground truth across 25 / 90 / 180 / -40 degrees, `Shape.Width` / `Height` (together or separately), and `ScaleWidth` from the top-left or from the middle all match one rule (the resize keeps a single anchor point, the untouched edge or the exact centre for a middle-anchored scale, fixed on screen once rotated), which the save path reproduces by moving `a:off` accordingly; the same fix and COM verification cover a plain (non-group) rotated shape resized directly, including both axes together in one edit (same sequential-correction fix, same 8-angle sweep). The one remaining non-right-angle gap is a ROTATED group resized directly AND having a child moved and/or resized in the SAME save. A fresh COM sweep settled two things here: first, the group's own resize committing BEFORE the child's edit and its tight re-wrap (matching this SDK's single-final-state save path) is the only order reachable at all - the reverse order diverges from it by up to 71,000 EMU (about 0.08 inch, visibly, not a rounding difference), because PowerPoint live-refits the group's box the instant a child changes, so whichever edit happens second composes against an already-refit box; a save built from one final element tree cannot recover which of a user's two separate actions happened first, so that reverse order is not a target this fix chases (it is `group-tight-rewrap.ts`'s pre-existing, documented "order A vs order B" boundary, now quantified). Within the reachable order, an 8-angle x 3-edit-combo (child moved, resized, moved+resized) sweep is byte-exact in 9 of 24 cases; the rest land up to 2 EMU (2/914400 inch) off COM ground truth on one or more of `a:off`'s x/y or `a:ext`'s width/height, with no consistent sign or axis. This is a distinct residual from the sequential-correction fix above, not the same one under a different name: applying that fix to this case's own self-resize step changes none of the 24 numbers (verified), and further decomposing the tight re-wrap step itself the same way makes it worse (6/24), as does carrying the intermediate center as an unrounded float through the whole chain (5/24, and it breaks an already-exact unrotated case) or using single-precision trig throughout (no change at all). `a:ext`'s height drifting in several cases - a value with no rotation term in this formula at all - points at PowerPoint computing this specific combination through a different internal path rather than a rounding-order fix reachable from black-box outputs. A follow-up COM experiment proves this rather than merely suspecting it: holding the child's FINAL position/size fixed and varying only the ORDER `GroupItems(1).Left`/`Top`/`Width`/`Height` are assigned (same four target values, one COM session, one save) changes the group's own saved `a:ext` by up to 589,402 EMU (0.64 inch) at 200 degrees and 115,531 EMU at 25 degrees - both orders individually byte-reproducible, neither one "more correct" than the other. PowerPoint live-refits the group's bounding box after EACH property assignment, not once per logical edit, so this specific combined case has no single correct answer to converge on: it has as many byte-exact answers as there are orderings a user could have entered the four numbers in, and a save built from one final element tree has no order to replay. The 9/24-exact, <=2 EMU sweep above (pinned against one such ordering's ground truth) is therefore already about as tight as a single-final-state save architecture can get; closing it to 0 for that one ordering would not generalize to any other equally valid one. See `group-tight-rewrap-own-box.ts` for the full investigation and proof, and `group-tight-rewrap.test.ts`'s `grp1st` sweep and order-sensitivity case for the COM-pinned numbers. |

### Animation authoring

An effect authored in the animation panel is reconciled into the slide's existing `p:timing` tree; the deck's own effects are left byte-identical. All 27 `p:animEffect/@filter` SMIL families resolve to a real reveal/conceal effect (25 of them entirely CSS-native; `wipe`/`barn` reuse the directional mask-reveal engine) that matches PowerPoint's own playback, including `pixelate`, which defaults to the same snap-to-end-state behaviour PowerPoint itself shows; see [Visual Effect Fidelity](/guide/visual-effects#pixelate-transition-filter) for the evidence and the opt-in mosaic this renderer can show instead. `image` has no gap to list either: see [OpenXML conformance](/architecture/openxml-conformance#extension-namespace-and-schema-edge-attributes).

### Detecting gaps at runtime

You do not have to guess whether a file hit a limitation. The load pipeline reports every unsupported or approximated construct it encounters on `data.warnings`, typed as `PptxCompatibilityWarning`:

```ts
interface PptxCompatibilityWarning {
	code: string; // stable machine-readable code
	message: string;
	severity: 'info' | 'warning';
	scope: 'presentation' | 'slide' | 'element' | 'save';
	slideId?: string; // present for slide/element-scoped warnings
	elementId?: string;
	xmlPath?: string; // where in the package the construct lives
}
```

Check `data.warnings` after `load()` (and after `save()`) if your application needs to surface fidelity notices to users or gate features per file.

See [Runtime Environments](/guide/runtime-environments) for where each part of `pptx-viewer` runs (browser / Node.js / Web Worker) and platform-specific behaviour that follows from the browser sandbox rather than from a missing feature.

## Framework viewers (React, Vue 3, Angular, Svelte 5, Vanilla JS)

::: warning CSS-based rendering trades some visual effects for fidelity elsewhere
Slides render as HTML/CSS rather than Canvas, giving sharp text at any zoom, native accessibility, and DOM interactivity. The tradeoff is that a few PowerPoint effects have no exact CSS equivalent and are approximated.
:::

A follow-up campaign (2026-09) re-ran the same 32-condition render-vs-COM comparison and found the elevation recalibration is a real regression for BOTH materials, not just `metal`: fresh COM ground truth for all 32 conditions matched the historical numbers above exactly (confirming real PowerPoint has not changed; only this filter's elevation input has), but scored against the CURRENT `elevationDeg`, `matte`'s mean absolute error rose from 34.8 to about 47.4 (`hardEdge` alone: COM 133/133 vs a render of about 73/14) even though `matte`'s `specularConstant` is negligible - a diffuse-side effect of `elevationDeg` itself, independent of the specular-saturation problem. A SEPARATE COM campaign (sampling the exact CENTER of a mid-grey `circle`-bevel square, i.e. the flat, non-bevelled interior, across `matte`/`metal`/`plastic` and 15 different `a:lightRig/@rig` values spanning elevation 54-90) measured all three materials PIXEL-IDENTICAL at every rig (e.g. `flat`: `rgb(127,127,127)` for all three, matching the raw unlit fill; `morning`: `rgb(112,108,98)` for all three): real PowerPoint's material response is zero on a flat normal at EVERY elevation, not merely small at low ones, confirming the washed-out-interior defect is real. Decoupling `feSpecularLighting` onto its own fixed, low `<feDistantLight>` elevation (chosen so the flat-region term is under 2/255 brightness units by closed-form calculation) was then tried and measured against the same 32 band conditions: it is not simply "lower is safer" - `hardEdge` (already low-relief) improved, but `angle` and `softRound` got substantially worse at every tested decoupled elevation (20deg: `metal`/`angle` highlight COM 141 vs rendered 154-214; 45deg: `metal`/`angle` highlight rendered 225-234, `metal`/`softRound` shadow rendered 234, i.e. saturating in the opposite direction), because a lower light elevation can align the half-vector more closely with a TILTED band normal than a high elevation does with the flat one, amplifying the band's own specular peak on steep-eroded profiles instead of only suppressing the flat interior. This decoupling attempt was measured, not landed. Re-tuning the specular constants for the new elevation, masking the specular layer to the actual curved band so a flat interior is zero by construction, or a full joint numerical re-fit of elevation/specular-elevation/constants/exponent/surfaceScale per material against this same COM ground truth all remain open; see `visual-3d-bevel-lighting.ts`'s module doc comment for the full re-measurement. The 12 `a:bevelT` height-map SHAPES themselves (which primitive chain each profile gets) remain reasoned from ECMA-376's descriptive semantics, not independently COM-verified pixel-for-pixel. The `a:lightRig/@rig` elevation table IS now COM-calibrated (2026-09): all 27 `ST_LightRigType` tokens were measured (mid-grey `matte`/`circle` square, 0.15in-from-edge highlight/shadow sampling, an independent `dir="t"` and `dir="r"` campaign per rig agreeing to under 1 brightness unit), and each rig's `elevationDeg` is the fit of its measured highlight/shadow contrast against a render-side sweep of the actual production SVG filter (see `visual-3d-bevel-lighting-tables.ts`'s `LIGHT_RIG_LIGHTING` doc comment for the full table and scripts). The earlier inconclusive `threePt`-vs-`harsh` check (measured contrast `threePt` 47, `harsh` -4) is now explained rather than merely noted: `harsh` is one of 10 rigs (also `balanced`, `twoPt`, the `*4` variant of each `legacy{Flat,Normal,Harsh}` family, and all 5 weather rigs `morning`/`sunrise`/`sunset`/`chilly`/`freezing`) whose measured highlight sits on the edge OPPOSITE `a:lightRig/@dir`, a per-rig direction inversion the previous single-`elevationDeg` model had no way to represent and is now COM-measured and applied. The 4 numbered variants within a legacy family (`legacyHarsh1`-`4` etc.) also turned out not to be interchangeable: COM measurement shows `*1`/`*3` are non-directional (no measurable gradient at this sample offset) while `*2` and `*4` are directional mirror images of each other, so each of the 27 tokens is now its own independently-measured table entry rather than 4 rigs sharing one reasoned value. The highlight / shadow band's width scaling with bevel depth is COM-confirmed (6pt vs 24pt); `extrusionClr` / `contourClr` colours are honoured. The scene's ground plane (`a:backdrop`) intentionally renders no shadow of its own: COM measurement (a shape with a real `a:outerShdw` plus a scene3d backdrop) confirmed PowerPoint shows no visible ground-plane artifact without a shadow effect present, and even with one a level or near-level backdrop is indistinguishable from no backdrop; a strongly tilted backdrop projects the shadow onto the tilted plane as a large, non-convex, sheared shape that no CSS `box-shadow` can represent, so the previous synthetic 2-D approximation (which fired even with no shadow effect, unlike PowerPoint) was removed rather than kept wrong. WordArt / text-body 3-D camera presets (`a:bodyPr/a:scene3d`) call the identical shape-level camera function, so a text box under a homography-covered preset produces the same `matrix3d` a shape of the same size would; COM-verified for `perspectiveHeroicLeftFacing` and `perspectiveLeft` (within ~1% of the shape measurement, via a convex hull of a filled-glyph "ink" rectangle) and visually confirmed for `isometricTopUp`, though that preset's extreme 45 deg roll made the automated corner-fit unreliable enough that no percentage is quoted for it. |
| WordArt envelope warps (`inflate` / `deflate` / `can` / `slant` / `fade` / `cascade` / ...) | Every `a:prstTxWarp` preset renders as true SVG text in all five bindings: the `slant` / `fade` / `cascade` and arch / wave / circle / ring / button family follow a bent `textPath` baseline, while the `inflate` / `deflate` / `can` envelope family renders per glyph, so glyph height and shear vary across the line the way PowerPoint's per-point outline warp does, for every paragraph of a multi-paragraph block too (paragraph separators are split by one shared `isParagraphSeparatorSegment` predicate, so a bare `"\n"` segment never renders as a glyph). `textCanUp` / `textCanDown`'s cylindrical top and bottom `arcTo` curves are parallel (same radius and centre, offset by a constant), so every glyph keeps the same height while still shearing along the arc (COM-verified); `inflate` / `deflate` and their variants genuinely vary glyph height. Cross-binding agreement within ~1.5 px in `e2e/text-warp-envelope-parity.spec.ts`. Each envelope glyph renders one of two ways depending on whether its actual font FILE is obtainable: a font embedded in the deck (parsed synchronously, no network) or a Google Fonts catalogue webfont whose bytes are fetched once resolved, wired identically into all five bindings (see [Visual effect fidelity](/guide/visual-effects)). When obtainable, the glyph's real vector outline is warped point-by-point - every on-curve point and off-curve Bezier control point mapped through the envelope curve at ITS OWN x, not the glyph's edges or centre (`text-warp-glyph-outline.ts`) - and rendered as one SVG `<path>`: exact in the sense that PowerPoint's own model is a per-point outline warp too, unit-tested for two provable invariants (a straight-line envelope reproduces the outline unchanged; a `can` preset keeps a constant vertical scale across the whole line, provable directly from the transcribed guide formulas). When no font file is obtainable (a system font with no embedded or catalogue match), the glyph falls back to an affine transform fit to the curve at the glyph's own left/right edge, split into up to 24 independently fitted, clipped sub-bands for an unusually wide glyph (`text-warp-glyph-slicing.ts`). Against PowerPoint COM renders the envelope-curve math itself matches to within ~0.2% mean / ~1.2% max at every preset and adjust value tested; the affine-fallback path stays within roughly 1-2% of PowerPoint for ordinary captions and, after slicing, a short caption of very wide glyphs at `can`'s extreme adjust value improves from ~6.7-6.9% / ~4.1-4.3% (4-8 glyphs sharing a line) to ~4.9-5.1% / ~2.9-3.1%. A ~1.1-1.2% residual at the box's literal edge is the transcribed `arcTo` curve model's own COM-measured deviation there (a near-vertical tangent at the arc's sweep boundary), not an artefact of the affine fit or the slicing technique, so it carries over unchanged to the exact outline-warp path too - both sample the identical curve function; closing it needs a from-scratch re-derivation of the guide-formula model itself, not more precision in how one glyph is warped. Whether a genuine outline-rendered `<path>` glyph at that literal-edge case has been independently re-measured against real PowerPoint (as opposed to the underlying curve function, which has) is open. ## EMF/WMF metafiles (`emf-converter` dependency)

::: info Not this repository's code
`emf-converter` is a separate npm package with its own repository; `pptx-viewer-core` only consumes it. The table below records what that package does today, so treat its own release notes as authoritative if the two ever disagree.
:::

::: warning Canvas API required
Metafile conversion needs `OffscreenCanvas` or `HTMLCanvasElement`. Pure Node.js without a canvas polyfill is not supported for EMF/WMF images (the rest of the core engine runs fine in Node).
:::

| Feature           | Status              | Notes                                                                       |
| ----------------- | ------------------- | --------------------------------------------------------------------------- |
| Gradient brushes  | Simplified          | GDI+ linear and path gradients render with their primary colour only.       |
| Raster operations | Not applied         | GDI ROP blending modes (XOR, NOT, AND, ...) are ignored.                    |
| Clipping          | Single path only    | Combined GDI region operations (union/intersect/exclude) are not supported. |
| Output size       | Clamped             | Output is clamped to 4096 x 4096 pixels.                                    |
| Text              | Browser font engine | Glyph metrics can differ from Windows GDI.                                  |

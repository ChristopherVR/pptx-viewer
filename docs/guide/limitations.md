# Limitations

::: warning Read this before adopting
`pptx-viewer` covers a large surface of the OpenXML specification, but some things are approximated, read-only, or bounded by the browser platform. This page lists what you **cannot** do, or can only do partially.
:::

## Core engine (`pptx-viewer-core`)

| Legacy binary `.ppt`        | Import only, never written                                   | `load()` detects the PowerPoint 97-2003 compound file and converts it through the OpenXML pipeline, so a `.ppt` opens and edits like any other deck. Saving always writes `.pptx` (as PowerPoint itself does), and a save name is re-extensioned accordingly. Password-protected `.ppt` files are decrypted the same way as encrypted `.pptx` files: `load(buffer, { password })` decrypts the legacy "RC4 CryptoAPI" scheme ([MS-OFFCRYPTO] 2.3.5.1) before conversion; without a password it throws `EncryptedFileError`, and a wrong password throws `IncorrectPasswordError`. ::: info What does round-trip
Everything else survives load, edit, and save: SmartArt text and structural edits, chart data and formatting, unknown vendor extensions (preserved verbatim), VBA macros, embedded fonts, and Strict OOXML files (normalised to Transitional on load, converted back to Strict on save by default). See [OpenXML conformance](/architecture/openxml-conformance).

"Survives" means the construct comes back, not that its editor-side identity does. Ink is the case to know about: a slide inked in PowerPoint round-trips as ink, but strokes drawn with this editor's own Draw tool are saved as a freeform shape and reopen as one (see [Ink and handwriting](#ink-and-handwriting)).

A file the editor never touched round-trips its **whole** timing tree verbatim, including everything the typed model does not expose (`p:tavLst` keyframes, `p:excl` exclusivity, and the nested time-node tree inside each `p:tmplLst`/`p:tmpl` template).
:::

### Animation authoring

An effect authored in the animation panel is reconciled into the slide's existing
`p:timing` tree rather than replacing it: the deck's own effects are left byte-identical,
and only the effects this editor added are ever retimed, resequenced or removed. The
editor records which time nodes it owns in a `p:ext` under `p:timing` so a later save can
tell them apart. The panel also surfaces a read-only anchor for each of the deck's own
effect groups (`PptxSlide.animationTimelineAnchors`), grounded in the same ordering space
as the editor's own animations, so drag-to-reorder can target any position in the full
sequence: moving an editor-authored effect past an anchor only repositions that effect's
`p:par` group among its siblings, never rewrites the anchor's own node.

Within that, these are the gaps:

### Ink and handwriting

Real pen ink is not a shape. PowerPoint writes it as a `p:contentPart` inside an
`mc:AlternateContent` branch, pointing at a separate InkML part that holds the
strokes in the digitizer's own device units. Reading that needs four things to
be right at once, so treat ink support as new: `contentPart` must be in the
`p14` capability set or the whole branch is skipped, InkML's compact difference
encoding must be decoded (PowerPoint writes `100 200,'40'46,"0"-5`, where the
sign doubles as the separator, so splitting on whitespace decodes a 31-point
stroke to a single point), brushes must be found where PowerPoint nests them in
`<inkml:definitions>` rather than as direct children, and the rewritten part
must have exactly one root element.

What holds today:

- A slide inked in PowerPoint loads, renders in **all five bindings**, and
  survives a save. Strokes are normalised from the part's device units into the
  element box, and each takes its colour, width and opacity from its own brush.
- Stroke pressure from the InkML `F` channel drives variable-width rendering.
- Drawing with the editor's own Draw tool captures each point's
  `PointerEvent.pressure` too, identically in all five bindings, and renders
  the in-progress and finished stroke at variable width whenever the pressure
  genuinely varies (a constant reading, the default for a mouse, renders as a
  single width, matching a real stylus's own behaviour). See the "Authored
  pressure" gap below for what happens to that pressure on save.
- A content part whose strokes were not edited keeps its original InkML part
  byte-for-byte; the part is rebuilt only when the stroke list actually changes.

What does not:

| Area                 | Status                           | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Draw tool output     | Freeform stroke shape, not ink   | Strokes drawn in the editor are saved as an `a:custGeom` shape with a stroked, unfilled path, not as the `p:contentPart` + InkML part PowerPoint's own pen writes. PowerPoint renders them correctly, but they reopen as a freeform shape rather than as editable ink, and they are not selectable with PowerPoint's ink tools.                                                                                                                                                                                                                                              |
| Authored pressure    | Captured and rendered; not saved | All five bindings' Draw tool records each point's `PointerEvent.pressure` and renders a genuinely varying stroke at variable width in the editor, matching a real stylus. That pressure does not survive a save: a drawn stroke is written as the `a:custGeom` shape above (not the `p:contentPart` + InkML part a real pen writes), and shape geometry has no per-point pressure channel to hold it. Pressure that came IN with a file is preserved and rendered.                                                                                                           |
| Multi-colour drawing | Collapses to the first stroke    | All strokes of one drawn ink element share one `a:ln`, so a drawing that mixes colours or widths saves with the first stroke's colour and width applied to every path.                                                                                                                                                                                                                                                                                                                                                                                                       |
| InkML channels       | `X`, `Y`, `F`, and pen tilt      | Position and pressure are used. A tilt-offset pair (`OTx`/`OTy`, or the `tiltX`/`tiltY` alias some digitizers use) or an `AZIMUTH` channel (paired with an optional `ALTITUDE`) is decoded into a per-point lean direction and strength, which widens each point perpendicular to the lean, approximating a calligraphic chisel-tip nib; a file with no tilt channel renders exactly as before. Timing and any other declared channel are still decoded positionally, as every channel always is, but have no consumer and are ignored.                                      |
| Curved traces        | Sampled along the curve          | Pressure rendering evaluates an SVG path's `C` / `Q` curves at several points along the curve itself (De Casteljau evaluation at multiple `t` steps per segment, not just at the control points and endpoint), and pressure is interpolated between the known samples at each step. Sample density scales with the curve's length, so pressure circles track a heavily curved stroke instead of trailing it. Sampling is by parametric `t`, not true arc length, so an extreme curve can still land points slightly closer together on one side of the curve than the other. |

### Detecting gaps at runtime

You do not have to guess whether a file hit a limitation. The load pipeline reports every unsupported or approximated construct it encounters on `data.warnings`, typed as `PptxCompatibilityWarning`:

```ts
interface PptxCompatibilityWarning {
	code: string; // stable machine-readable code
	message: string;
	severity: 'info' | 'warning';
	scope: 'presentation' | 'slide' | 'element' | 'save';
	slideId?: string; // present for slide/element-scoped warnings
	elementId?: string;
	xmlPath?: string; // where in the package the construct lives
}
```

Check `data.warnings` after `load()` (and after `save()`) if your application needs to surface fidelity notices to users or gate features per file.

## Runtime environments

| Environment              | Works     | Caveats                                                                                                                                                                              |
| ------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Browser                  | Yes       | The full feature set: parsing, rendering, editing, export, collaboration.                                                                                                            |

| Web Worker               | Core only | Same scope as Node.js: the engine has no DOM dependency.                                                                                                                             |

## Framework viewers (React, Vue 3, Angular, Svelte 5, Vanilla JS)

::: warning CSS-based rendering trades some visual effects for fidelity elsewhere
Slides render as HTML/CSS rather than Canvas, giving sharp text at any zoom, native accessibility, and DOM interactivity. The tradeoff is that a few PowerPoint effects have no exact CSS equivalent and are approximated.
:::

| 3D extrusion / bevel / contour / material (`a:sp3d`)                                    | CSS `box-shadow` / `filter` approximation, not true geometry or lighting; `extrusionClr` / `contourClr` colours are honoured                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Reflections (`a:effectLst` reflection), on shapes, pictures **and** text runs           | A mirrored sibling node (`transform: scaleY(-1)` + `scale`/`skew`/`rotate`, faded with a `mask-image` gradient), painted with the element's own resolved fill / picture content, or the same text for a run - not `-webkit-box-reflect`, which Firefox never implemented at all (reflections rendered nowhere in Firefox before this), so it now renders identically in Firefox, Chromium and Safari. `@sx` / `@sy`, `@kx` / `@ky`, `@rot`, `@fadeDir` and `@algn` are all honoured for a shape or picture **and** for a text run: core's text-run parser extracts the full `a:rPr/a:effectLst/a:reflection` attribute set the same way it does for a shape's, so an authored value for any of them round-trips through a save. For a shape or picture, the mirrored content is the element's resolved fill (colour / gradient / pattern / image), not a pixel-perfect clone of its text/children. |
| Soft edges (`a:softEdge`)                                                               | SVG alpha-feather filter (feathers the edge, not a whole-element blur)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Path gradients                                                                          | `circle` and `shape` types: an elliptical radial gradient. `rect` type: an SVG image of nested, axis-aligned rectangle bands reproducing the true square-cornered (Chebyshev-distance) field PowerPoint shades toward, including a non-square `a:fillToRect` target rectangle, in place of the single ellipse this used to fall back to; no native CSS/SVG radial gradient has square corners, so a plain `radial-gradient()` cannot express it at all. A freeform (`a:custGeom`) shape still paints any path type as one elliptical SVG radial gradient (its own fill path, separate from the CSS background path above).                                                                                                                                                                                                                                                                         |

| Cinematic 3-D transitions (`cube`, `box`, `flip`, `rotate`, `pageCurl`, `origami`, ...) | Animated via CSS keyframes (perspective / rotate / curl), not a true 3-D render. `box` reuses the `cube` keyframes: it is Cube's inverted twin and has no distinct CSS approximation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

| Morph transitions                                 | Partial                                               | Elements are matched across the two slides by explicit `!!` naming, `a16:creationId`/native shape-id identity, and same-type proximity (claimed closest pair first across the whole slide, not element by element in document order, so a nearby true match is no longer lost to a farther element that happened to be listed first). A plain Selection Pane name with no `!!` prefix is not a signal PowerPoint's own Morph honours (confirmed against real PowerPoint), so renaming two shapes to the same name does not make them morph into each other. An element that genuinely has no counterpart on the next slide still crossfades instead of morphing, which mirrors PowerPoint's own behaviour.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Chart direct manipulation                         | Varies by chart kind                                  | Bar, line, area, scatter, and bubble marks can be dragged to new values on the canvas (click a mark to select, double-click the title to rename); every mark also shows a hover tooltip. Pie, doughnut, radar, stacked/percent-stacked, map, and surface marks are click-to-select with values edited in the inspector (no drag-to-value); all of them, including surface, now show a hover tooltip too. An interactive 3D surface-chart scene (camera rotate/zoom via `three.js` `OrbitControls`) is wired into all five bindings' chart views, honours the authored `c:view3D` rotation for its initial camera, paints authored `c:floor` / `c:sideWall` / `c:backWall` colours and per-band `c:bandFmts` colours on the mesh, and raycasts the pointer against the mesh so the canvas itself carries the hovered facet's tooltip text (there is no SVG mark on a WebGL mesh to attach a native `<title>` to); browsers without `three.js` installed fall back to a flat/isometric SVG projection, which paints the same floor/wall/band colours and titles each facet's polygon the same way as every other chart kind. All five bindings support the full interaction set.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `bar3D` / `line3D` / `area3D` / `pie3D` rendering | Oblique-projection illusion, not a projected 3D scene | These four keep their flat 2D mark geometry and get an additive oblique-projection depth pass (shaded top/side faces, driven by `c:view3D`'s `rotX` / `rotY` / `depthPercent`) rather than a true projected 3D plot cube; a full camera/projection rewrite of the shared cartesian layout (shared with the 2D `bar` / `line` / `area` / `pie` types) was judged disproportionate to attempt wholesale. Within that illusion, a clustered `bar3D` chart now separates each series onto its own depth plane with correct back-to-front occlusion (previously every series shared one depth plane, which was the largest visible gap versus PowerPoint); stacked/percent-stacked `bar3D` keeps its series coplanar, matching a single physical stack. Authored `c:floor` / `c:sideWall` / `c:backWall` colours are painted as background panels behind `bar3D` / `line3D` / `area3D` (previously parsed but never drawn); `pie3D` has no plot rectangle to wall in, so it is unaffected by that panel treatment. `pie3D` now also gets elliptical tilt foreshortening: its disc, leader lines and data labels are squashed vertically about the pie's centre by `cos(rotX)` (clamped so an extreme `rotX` cannot collapse it to a sliver), approximating the tilted ellipse PowerPoint shows instead of staying a perfect circle at any `rotX`. This is still the same oblique illusion, not a projected ellipse from an actual camera, and the squash is driven only by `rotX`; `rotY` continues to only steer the shared depth vector's horizontal offset (same as the other three types), not an additional rotation of the pie face itself. |

## EMF/WMF metafiles (`emf-converter` dependency)

::: info Not this repository's code
`emf-converter` is a separate npm package with its own repository; `pptx-viewer-core` only consumes it. The table below records what that package does today, so treat its own release notes as authoritative if the two ever disagree.
:::

::: warning Canvas API required
Metafile conversion needs `OffscreenCanvas` or `HTMLCanvasElement`. Pure Node.js without a canvas polyfill is not supported for EMF/WMF images (the rest of the core engine runs fine in Node).
:::

| Feature           | Status              | Notes                                                                       |
| ----------------- | ------------------- | --------------------------------------------------------------------------- |
| Gradient brushes  | Simplified          | GDI+ linear and path gradients render with their primary colour only.       |
| Raster operations | Not applied         | GDI ROP blending modes (XOR, NOT, AND, ...) are ignored.                    |
| Clipping          | Single path only    | Combined GDI region operations (union/intersect/exclude) are not supported. |
| Output size       | Clamped             | Output is clamped to 4096 x 4096 pixels.                                    |
| Text              | Browser font engine | Glyph metrics can differ from Windows GDI.                                  |

# Limitations

::: warning Read this before adopting
`pptx-viewer` covers a large surface of the OpenXML specification, but some things are approximated, read-only, or bounded by the browser platform. This page lists what you **cannot** do, or can only do partially.
:::

::: info What does round-trip
Everything else survives load, edit, and save: SmartArt text and structural edits, chart data and formatting, unknown vendor extensions (preserved verbatim), VBA macros, embedded fonts, and Strict OOXML files (normalised to Transitional on load, converted back to Strict on save by default). See [OpenXML conformance](/architecture/openxml-conformance).

"Survives" means the construct comes back, not always that its editor-side identity does. Ink used to be the case to know about here (a slide inked in PowerPoint round-tripped as ink, but a stroke drawn with this editor's own Draw tool downgraded to a freeform shape on save); both now save as the same `p:contentPart` + InkML representation, so a drawn stroke reopens as ink too (see [Ink and handwriting](#ink-and-handwriting)).

A file the editor never touched round-trips its **whole** timing tree verbatim, including everything the typed model does not expose (`p:tavLst` keyframes, `p:excl` exclusivity, and the nested time-node tree inside each `p:tmplLst`/`p:tmpl` template).
:::

### Animation authoring

An effect authored in the animation panel is reconciled into the slide's existing
`p:timing` tree rather than replacing it: the deck's own effects are left byte-identical,
and only the effects this editor added are ever retimed, resequenced or removed. The
editor records which time nodes it owns in a `p:ext` under `p:timing` so a later save can
tell them apart. The panel also surfaces a read-only anchor for each of the deck's own
effect groups (`PptxSlide.animationTimelineAnchors`), grounded in the same ordering space
as the editor's own animations, so drag-to-reorder can target any position in the full
sequence: moving an editor-authored effect past an anchor only repositions that effect's
`p:par` group among its siblings, never rewrites the anchor's own node.

### Ink and handwriting

Real pen ink is not a shape. PowerPoint writes it as a `p:contentPart` inside an
`mc:AlternateContent` branch, pointing at a separate InkML part that holds the
strokes in the digitizer's own device units. Both reading and writing that
correctly need several things to be right at once, verified against real
PowerPoint (COM automation opening the produced file), not just against this
project's own reader:

- `contentPart` must be in the `p14` capability set (`mc:Choice
Requires="p14"`) or the whole branch is skipped on load; a written branch
  that instead declares `a14` (a real, but unrelated, MC namespace) opens as a
  package PowerPoint itself reports "corrupted and unreadable" (0x80070570),
  even though it passes this project's own lenient reader and internal schema
  validator. The gap between "this project's own reader accepts it" and
  "PowerPoint accepts it" is exactly the trap here.
- A `p:contentPart`'s non-visual properties and transform (`nvContentPartPr`,
  `cNvPr`, `cNvContentPartPr`, `nvPr`, `xfrm`) must be `p14:`-qualified, not
  `p:`-qualified, and that id must be counted by the shape-id-uniqueness
  validator (it can otherwise collide with an ordinary shape's id) or the same
  0x80070570 failure results.
- InkML's compact difference encoding must be decoded on read (PowerPoint
  writes `100 200,'40'46,"0"-5`, where the sign doubles as the separator, so
  splitting on whitespace decodes a 31-point stroke to a single point).
  Writing does NOT need to reproduce that encoding: plain per-point decimal
  values open in real PowerPoint too, once the structural points below hold.
- Brushes, and the shared trace `traceFormat`, must sit inside
  `<inkml:definitions>` (a `context`/`inkSource` wrapping the format, `brush`
  as a sibling), not as direct children of the `<ink>` root, and every
  identifiable element (`context`, `inkSource`, `brush`) must be keyed by the
  InkML/XML spec's `xml:id`, not a bare `id`. A flat, un-nested structure with
  a bare `id` passes this project's own reader and internal validator but is
  rejected by real PowerPoint.
- Each `<trace>` needs both `contextRef` and `brushRef`; `brushRef` alone is
  rejected.
- The rewritten part must have exactly one root element.

What holds today:

- A slide inked in PowerPoint loads, renders in **all five bindings**, and
  survives a save. Strokes are normalised from the part's device units into the
  element box, and each takes its colour, width and opacity from its own brush.
- Stroke pressure from the InkML `F` channel drives variable-width rendering.
- Drawing with the editor's own Draw tool captures each point's
  `PointerEvent.pressure`, identically in all five bindings, and renders the
  in-progress and finished stroke at variable width whenever the pressure
  genuinely varies (a constant reading, the default for a mouse, renders as a
  single width, matching a real stylus's own behaviour).
- **A stroke drawn with the Draw tool now saves as the same `p:contentPart` +
  InkML representation PowerPoint's own pen writes**, not a static `a:custGeom`
  freeform shape: it reopens as editable ink, is selectable with PowerPoint's
  own ink tools, and round-trips through this project's own reader as a
  `contentPart` element. Each stroke gets its own InkML brush, so a drawing
  that mixes colours or widths keeps every stroke's own colour and width
  (previously all strokes collapsed onto the first one's `a:ln`). Each
  stroke's captured `PointerEvent.pressure` is authored onto its trace's `F`
  channel and reads back as variable width, the same way pressure from a real
  PowerPoint-authored file does. This was verified against real PowerPoint
  over COM automation, not only this project's own reader: a multi-stroke,
  multi-colour, variable-pressure drawing saves, reopens, and reports as
  `Shape.Type = msoInk` (23) in PowerPoint itself.
- A content part whose strokes were not edited keeps its original InkML part
  byte-for-byte; the part is rebuilt only when the stroke list actually changes.

What does not:

| Area           | Status                      | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| InkML channels | `X`, `Y`, `F`, and pen tilt | Position and pressure are used. A tilt-offset pair (`OTx`/`OTy`, or the `tiltX`/`tiltY` alias some digitizers use) or an `AZIMUTH` channel (paired with an optional `ALTITUDE`) is decoded into a per-point lean direction and strength, which widens each point perpendicular to the lean, approximating a calligraphic chisel-tip nib; a file with no tilt channel renders exactly as before. Timing and any other declared channel are still decoded positionally, as every channel always is, but have no consumer and are ignored. The Draw tool itself never authors a tilt channel: browser `PointerEvent` exposes `tiltX`/`tiltY` on supporting hardware, but this editor does not yet capture or write it, so a stroke drawn here always round-trips with position and pressure only, never a calligraphic lean. |
| Curved traces  | Sampled along the curve     | Pressure rendering evaluates an SVG path's `C` / `Q` curves at several points along the curve itself (De Casteljau evaluation at multiple `t` steps per segment, not just at the control points and endpoint), and pressure is interpolated between the known samples at each step. Sample density scales with the curve's length, so pressure circles track a heavily curved stroke instead of trailing it. Sampling is by parametric `t`, not true arc length, so an extreme curve can still land points slightly closer together on one side of the curve than the other.                                                                                                                                                                                                                                              |

### Detecting gaps at runtime

You do not have to guess whether a file hit a limitation. The load pipeline reports every unsupported or approximated construct it encounters on `data.warnings`, typed as `PptxCompatibilityWarning`:

```ts
interface PptxCompatibilityWarning {
	code: string; // stable machine-readable code
	message: string;
	severity: 'info' | 'warning';
	scope: 'presentation' | 'slide' | 'element' | 'save';
	slideId?: string; // present for slide/element-scoped warnings
	elementId?: string;
	xmlPath?: string; // where in the package the construct lives
}
```

Check `data.warnings` after `load()` (and after `save()`) if your application needs to surface fidelity notices to users or gate features per file.

## EMF/WMF metafiles (`emf-converter` dependency)

::: info Not this repository's code
`emf-converter` is a separate npm package with its own repository; `pptx-viewer-core` only consumes it. The table below records what that package does today, so treat its own release notes as authoritative if the two ever disagree.
:::

::: warning Canvas API required
Metafile conversion needs `OffscreenCanvas` or `HTMLCanvasElement`. Pure Node.js without a canvas polyfill is not supported for EMF/WMF images (the rest of the core engine runs fine in Node).
:::

| Feature           | Status              | Notes                                                                       |
| ----------------- | ------------------- | --------------------------------------------------------------------------- |
| Gradient brushes  | Simplified          | GDI+ linear and path gradients render with their primary colour only.       |
| Raster operations | Not applied         | GDI ROP blending modes (XOR, NOT, AND, ...) are ignored.                    |
| Clipping          | Single path only    | Combined GDI region operations (union/intersect/exclude) are not supported. |
| Output size       | Clamped             | Output is clamped to 4096 x 4096 pixels.                                    |
| Text              | Browser font engine | Glyph metrics can differ from Windows GDI.                                  |
